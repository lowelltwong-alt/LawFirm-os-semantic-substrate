# Master Roadmap

## Execution Control

Roadmap execution order is controlled by `docs/roadmap/READINESS_GATES.md`.
A phase advances only when the applicable readiness gate passes.

## Purpose

Provide one coherent roadmap for how the repository evolves from validated kernel to operational pilot system.

## Phase 0: Canonical Spine
Lock the canonical design authority and validation path.

## Phase 1: Substrate Definition
Define the machine-readable doctrinal and comparison substrate.

## Phase 2: Validation Hardening
Add structured schema, YAML, SHACL, and ID validation around the substrate.

## Phase 3: Assertion, Provenance, and Trust Boundaries
Introduce governed assertion objects, provenance activities, and graph partition boundaries.

## Phase 4: Alignment Rubric Layer
Add machine-readable comparison assessments with scope, translation burden, evidence sufficiency, and review posture.

## Phase 5: Operational Governance and Pilot Slice
Add action types, object sets, reviewer roles, pilot slices, and promotion posture.

## Phase 6: Semantic Graph Stack
Add JSON-LD contexts, named-graph manifests, SHACL seed shapes, projection contracts, retrieval sidecars, and bounded semantic packaging.

## Phase 7: External Standards Rationale
Explain why standards are adopted now, used selectively, or deferred to watchlist status.

## Phase 8: Sponsor-Ready Pilot Layer
Add executive framing, answer payloads, source registry, Azure target architecture, access model, ingestion policy, evaluation plan, and gold questions.

## Phase 9: Bounded Runtime Continuation
Add one real query surface, one steward-owned workflow, one governed retrieval surface, and one measurable operational outcome.

## Design Rule Across All Phases

Every phase must:
- preserve the canonical spine
- remain validation-aligned
- extend additively
- improve operational usefulness
- avoid parallel ontology systems

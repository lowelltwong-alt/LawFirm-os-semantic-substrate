# Canonical DNA Questions

Author: Lowell T. Wong

## Purpose

This file defines the single canonical DNA question model for the repository.

Future AI systems, contributors, validators, governance layers, retrieval systems, and enterprise learning workflows should use this file as the authoritative question set for understanding what every first-order governed object must be able to answer.

## Canonical DNA Question Model

Every important governed object should be interpretable through these questions.

### Core identity and placement
1. What is this?
2. Where is it?
3. What type of object is it?
4. What layer, domain, and module does it belong to?

### Structural and relational
5. What is it connected to?
6. What depends on it?
7. What does it depend on?

### Lineage and evidence
8. What is it derived from?
9. What evidence or source supports it?
10. What changed before this existed?

### Governance and trust
11. What state is it in?
12. How trustworthy is it?
13. What authority zone does it belong to?
14. What validation rules apply to it?

### AI and execution posture
15. Should AI use it, and how strongly?
16. What breaks if it changes?
17. Should it be promoted, revised, deprecated, or retired?
18. What should the system learn from using it?

### Pressure, exceptions, and learning
19. What pressure or exception patterns does this object reveal?
20. What happens when this object fails, is overridden, or creates ambiguity?
21. Which learning loop should receive that signal?
22. Should the resulting learning change retrieval, workflow, taxonomy, ontology, or governance?

## Rule

If an object cannot answer these questions at the appropriate level of detail, it is incomplete relative to the repository's DNA model.

## Application

This canonical question model should guide:
- schema design
- artifact design
- claim design
- address design
- validation design
- retrieval design
- workflow design
- exception-event design
- enterprise learning loops

## Interpretive note

These questions apply not only to stable governed objects such as claims, artifacts, and nodes, but also to governed learning objects such as:

- exception events
- pressure vectors
- promotion candidates
- review packets
- retrieval miss cases
- workflow escalation cases

This is important because the repository is not only trying to model what is true.
It is also trying to preserve what the system learns when the current model proves incomplete, weak, or in tension with reality.

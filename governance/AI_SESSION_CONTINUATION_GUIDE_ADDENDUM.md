# AI Session Continuation Guide Addendum

Author: Lowell T. Wong

## Purpose

This addendum captures a critical synthesis decision for future AI sessions working on this repository:

The repository should preserve its **fractal / recursive / DNA-like shell as the master architecture**, while importing a stronger practical governance spine from operational ontology patterns.

This is the intended merged model.

## Core Synthesis

The repository's deeper advantage is not merely that it has files, schemas, and folders.
Its deeper advantage is that it is designed as a recursive and fractal operating grammar in which major objects can be governed through a repeatable structural pattern.

At the same time, practical law-firm ontology patterns contribute important implementation strengths that should be imported rather than ignored.

The right move is therefore:
- keep the fractal shell as the master architecture
- import the practical governance spine into that shell

## What the Fractal Shell Must Preserve

Future sessions should preserve these as architectural non-negotiables:
- recursive / fractal design
- multi-scale addressability
- first-order artifact thinking
- separation of identity vs structural address
- claim-centered reasoning
- trust-aware ontology design
- lineage and attribution chains
- deterministic / probabilistic interoperability

## What Should Be Imported Into the Shell

Future sessions should explicitly preserve and strengthen the following imported governance primitives:

### 1. Claim containers
Important assertions should not be modeled as bare edges alone.
Claims should be first-class containers that can carry:
- subject
- predicate
- object
- assertion type
- authority context
- evidence
- confidence
- review status

### 2. Authority / trust zones
Major objects and claims should carry authority and permission context.
Examples include:
- public
- internal-general
- internal-km-approved
- practice-restricted
- client-restricted
- matter-restricted
- ethical-wall-restricted
- experimental-ai

### 3. Asserted / inferred / hypothesis separation
These must remain visibly distinct.
They should not be flattened into a single undifferentiated relationship layer.

### 4. Retrieval neighborhood templates
AI retrieval should be governed by structured neighborhood logic, not only by unconstrained search or similarity.
Neighborhood templates should remain a first-class pattern for AI context expansion.

### 5. Validation + CI as part of ontology DNA
Validation is not optional tooling.
Validation, schema checks, and CI workflows are part of the operating integrity of the repository.

### 6. Minimal v1 kernel discipline
Do not model everything at once.
Preserve the discipline of building from the smallest useful kernel.

### 7. Dual-surface thinking
Preserve the distinction between:
- human-readable surface
- machine-readable surface

Over time, this may evolve toward explicit export targets such as JSON-LD / RDF and property-graph oriented representations.

## Most Important Practical Rule

Future sessions should not flatten the repository into a conventional folder-based ontology repo.

Repository folders are deployment layout and implementation scaffolding.
They are not the deepest ontology truth.

The deeper ontology truth remains:
- recursive addressability
- governed objects
- claim containers
- lineage
- trust
- retrieval logic

## Current Best Summary

A useful way to think about the merged design is:
- the fractal shell is the deeper brain
- the practical governance spine is the stronger skeleton

The goal is not to choose between them.
The goal is to merge them correctly.

## Priority Guidance for Future AI Sessions

When improving this repository, follow this order:

1. Preserve the fractal shell.
2. Strengthen claim containers.
3. Make authority and trust zones more explicit.
4. Preserve asserted / inferred / hypothesis separation.
5. Add stronger validation and CI.
6. Keep the v1 kernel minimal.
7. Expand retrieval through neighborhood templates.
8. Only then broaden the domain surface.

## Final Note

If future sessions are forced to choose between:
- architectural depth
- implementation neatness

prefer architectural depth first, then bring implementation into alignment.

The repository's distinctive value is that it is trying to become:
- a document architecture
- a decision architecture
- a taxonomy architecture
- an ontology architecture
- a retrieval architecture
- eventually an agent-operable operating system

That broader ambition should remain visible and protected.
